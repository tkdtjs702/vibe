# 구현 계획서

## 목적과 범위

이 문서는 `PRD.md`, `ARCHITECTURE.md`, `AGENTS.md`를 바탕으로 demo 모드를 실제 KOBIS 연동·Supabase 캐시 기반 서비스로 확장하기 위한 구현 순서와 계약을 정의한다. 브라우저는 내부 API만 호출하며, `KOBIS_API_KEY`와 `SUPABASE_SECRET_KEY`는 서버 환경의 `.env.local`에서만 사용한다.

## 1. 화면 상태

| 상태 | 진입 조건 | 화면 처리 | 사용자 동작 | API/데이터 의미 |
| --- | --- | --- | --- | --- |
| 초기/로딩 | 날짜·기간 변경 또는 재시도 직후 | 기존 표와 구분되는 로딩 안내를 표시하고 중복 요청을 막는다. | 대기 또는 취소 가능한 다음 조회 | 요청 진행 중이며 결과는 아직 확정되지 않음 |
| 성공 | `200`이고 `data.entries`가 1건 이상 | 순위, 영화명, 개봉일, 매출, 관객수, 누적 관객수를 표로 표시한다. | 영화명으로 클라이언트 측 필터링 | 검증된 숫자형 데이터 |
| 정상 빈 결과 | `200`이고 `entries`가 0건 | “선택한 날짜와 기간의 박스오피스 데이터가 없습니다. 다른 날짜 또는 기간을 선택해 보세요.”를 표시한다. | 날짜·기간 변경 | KOBIS의 정상 빈 응답을 캐시했거나 받아온 경우 |
| 검색 결과 없음 | 성공 데이터는 있으나 검색 필터 결과가 0건 | “’{검색어}’와 일치하는 영화가 없습니다.”를 표시하고 원본 목록은 유지한다. | 검색어 수정 또는 검색 초기화 | API 오류나 정상 빈 결과가 아님 |
| 입력 오류 | 날짜·기간 형식이 유효하지 않아 API가 `400`을 반환 | 입력 항목 가까이에 안전한 안내를 표시한다. | 올바른 값으로 수정 | 서버가 외부 호출 전에 거절 |
| 외부/내부 오류 | `502`, `503`, `504` 또는 예기치 않은 `5xx` | “데이터를 불러오지 못했습니다. 잠시 후 다시 시도해 주세요.”와 재시도 버튼을 표시한다. 상세 오류·키·URL은 노출하지 않는다. | 같은 조건으로 재시도 | 외부 API·DB·내부 처리 실패 |
| 오래된 캐시 성공 | 외부 갱신은 실패했으나 마지막 성공 캐시가 있을 때 | 표를 유지하고 “최신 데이터 갱신에 실패해 이전 저장본을 표시합니다.”를 보조 안내로 표시한다. | 재시도 | `meta.stale: true`인 제한적 성공 |

## 3. 내부 API 계약

### 목록 API

`GET /api/box-office?date=YYYY-MM-DD&periodType=daily|weekly|weekend`

| 구분 | 정의 |
| --- | --- |
| 요청 파라미터 | `date`는 실재하는 ISO 날짜, `periodType`은 `daily`, `weekly`, `weekend` 중 하나이며 모두 필수다. 영화명 검색어는 내려받은 성공 목록에만 적용하므로 API 파라미터로 보내지 않는다. |
| 성공 `200` | `{ "data": { "entries": [{ "movieCd": "string", "movieNm": "string", "rank": 1, "openDt": "YYYY-MM-DD", "salesAmt": 0, "audiCnt": 0, "salesAcc": 0, "audiAcc": 0 }] }, "meta": { "date": "YYYY-MM-DD", "periodType": "daily", "source": "cache|kobis", "stale": false, "fetchedAt": "ISO-8601", "expiresAt": "ISO-8601" } }` |
| 정상 빈 결과 | `200`과 같은 구조를 사용하되 `data.entries`는 빈 배열, `meta.isEmpty`는 `true`다. |
| `400 Bad Request` | 날짜 형식·실재 날짜·기간 유형이 유효하지 않을 때. `{ "error": { "code": "INVALID_REQUEST", "message": "요청 값을 확인해 주세요." } }` |
| `502 Bad Gateway` | KOBIS가 비정상 응답, 스키마 오류, 인증 외 외부 응답 오류를 반환하고 사용 가능한 저장본도 없을 때. |
| `503 Service Unavailable` | DB가 일시적으로 사용 불가하거나 KOBIS의 명시적 서비스 제한/점검으로 응답할 수 없을 때. |
| `504 Gateway Timeout` | KOBIS 호출이 제한 시간을 넘고 사용 가능한 저장본도 없을 때. |

### 인사이트 API

`GET /api/insights?days=7|14|30&top=5|10`

`data`에는 일간 데이터만으로 집계한 `dailySales`, `topMovies`, `summary`를, `meta`에는 집계 기간·누락 일자·생성 시각을 포함한다. 요청값 오류는 `400`, 원본 일간 데이터의 확보 실패는 위 목록 API와 같은 `502`/`503`/`504` 정책을 적용한다. 주간·주말 데이터는 일별 추이에 합산하지 않는다.

## 4. 목록 요청 처리와 캐시 정책

처리 순서는 다음과 같다.

`입력 검증 → 캐시 조회 → 외부 호출 → 정규화·저장 → 저장본 대조 → 내부 API 응답`

| 단계 | 수행 내용 | 초기 운영값 | 실패 시 처리 |
| --- | --- | --- | --- |
| 1. 입력 검증 | 날짜와 기간 유형을 검증하고 KOBIS 엔드포인트를 서버에서만 선택한다. | 외부 호출 전 즉시 수행 | `400`을 반환하고 DB·KOBIS를 호출하지 않는다. |
| 2. 캐시 조회 | `(period_type, target_date)`로 유효한 저장본을 조회한다. 빈 결과 캐시도 조회 대상이다. | 일간 TTL 6시간, 주간·주말 TTL 24시간; 모두 환경변수로 조정 가능 | DB 읽기 실패는 `503`; 마지막 성공 저장본을 신뢰성 있게 읽을 수 있으면 stale 경로를 검토한다. |
| 3. 외부 호출 | 캐시 미스·만료 시 KOBIS API를 서버에서 호출한다. 동일 키의 동시 갱신은 잠금 또는 upsert 충돌 처리로 한 번만 수행한다. | 연결 3초, 전체 응답 8초, 재시도는 최대 1회(일시적 네트워크 오류만) | 타임아웃은 `504`, 서비스 제한·점검은 `503`, 비정상 응답은 `502`으로 분류한다. 만료된 마지막 성공 저장본이 있으면 `200` + `meta.stale: true`로 제한적으로 반환한다. |
| 4. 정규화·저장 | `movieCd`는 문자열로 유지한다. `rank`, `salesAmt`, `audiCnt`, `salesAcc`, `audiAcc`는 정수 형식·범위·안전한 정수 여부를 검증해 숫자로 바꾼 뒤 트랜잭션/upsert로 저장한다. | 금액·관객수는 음수 불가, 순위는 1 이상 | 한 항목이라도 필수 형식 검증에 실패하면 부분 저장하지 않고 `502`로 처리한다. DB 쓰기 실패는 `503`이다. |
| 5. 저장본 대조 | 저장 직후 해당 기간과 실적 행을 다시 읽어 유일 키, 행 수, 핵심 필드가 정규화 결과와 같은지 대조한 뒤 응답을 만든다. | 호출당 1회, 읽기 제한 시간 2초 | 대조 실패 시 성공으로 응답하지 않고 `503`으로 기록·반환한다. 이미 저장된 불완전 데이터는 운영 절차로 조사한다. |

TTL과 제한 시간은 시작값이며, 배포 전 KOBIS 이용 조건과 Vercel Hobby·Supabase Free의 최신 제한을 확인해 환경변수 값과 운영 문서에 확정한다. API 키·DB 비밀 키·원본 오류 본문은 응답과 로그에 포함하지 않는다.

## 5. 구현 우선순위와 완료 기준

| 우선순위 | 구현 순서 | 핵심 범위 | 완료 확인 기준 |
| --- | --- | --- | --- |
| P0 | 1. 데이터 계약·검증 모듈 | KOBIS 원본 타입, 숫자 문자열 검증, API 응답 타입, 실패 분류 단위 테스트 | 유효 값은 숫자로 변환되고, 빈 값·문자·음수·안전 범위 밖 값은 거부되며 `movieCd`는 문자열로 유지되는 테스트가 통과한다. |
| P0 | 2. Supabase 스키마·마이그레이션 | `movies`, `query_periods`, `period_performances` 및 캐시 메타데이터, PK/FK/유일 제약/인덱스 | 빈 응답도 저장 가능하고 같은 기간의 중복 저장이 불가능하며, 롤백 가능한 마이그레이션 검증을 통과한다. |
| P0 | 3. 캐시 저장소·KOBIS 서버 클라이언트 | TTL 판정, timeout, 정상 빈 결과 캐싱, stale fallback, 비밀 키 서버 한정 | cache hit은 외부 호출 없이 응답하고, miss는 저장·대조 후 응답하며, timeout/DB 실패/빈 결과가 계약대로 분리되는 테스트가 통과한다. |
| P0 | 4. 실제 `GET /api/box-office` | 입력 검증부터 응답 계약까지 연결, `DATA_MODE=live` 활성화 | `400`, 성공, 정상 빈 결과, `502`/`503`/`504`, stale 성공의 통합 테스트와 타입 검사가 통과한다. |
| P0 | 5. F1 live 연결 | demo UI를 동일 계약의 live API에 연결하고 5개 화면 상태를 완성 | 날짜·일간/주간/주말·검색·재시도와 각 상태의 Playwright 시나리오가 통과한다. |
| P1 | 6. 인사이트 API·F2 | 최근 7/14/30일 일간 매출 추이, Top 5/10, 보조 지표 | 일간 데이터만 집계한다는 단위·통합 테스트, Top 정렬·합계 테스트, F2 화면 테스트가 통과한다. |
| P1 | 7. 관측·배포 점검 | 안전한 구조화 로그, 환경 변수 점검, 무료 플랜 한도 확인, 운영 문서 | 키 비노출 확인, 빌드·린트·타입 검사·단위/E2E 테스트 통과, Vercel/Supabase 배포 전 점검표 완료가 확인된다. |

각 순서는 이전 순서의 완료 기준과 관련 테스트를 통과한 뒤에만 시작한다. 스키마·외부 서비스 설정·배포의 실제 변경은 별도 승인 후 수행한다.

## 검증 보고 방식

구현 단계마다 일반 모드 결과를 `통과`, `실패`, `미실행`으로 구분해 보고한다. 실패는 재현 조건·원인·수정·재검증 결과를 함께 남기고, 미실행은 이유와 실행 전제 조건을 남긴다. API 파싱·DB 저장·캐시·지표·상태 전환 변경에는 `.agents/skills/box-office-verification/SKILL.md`의 검증 절차를 적용한다.
